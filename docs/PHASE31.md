# Phase 31 — Native local video playback (QEMU baseline)

MyOS can decode and display a local MYV1 clip in its own framebuffer while
playing the clip's unsigned 8-bit mono PCM through the QEMU Sound Blaster 16.
The player runs in the kernel and is launched from the Shell. This is a
deliberately small, original format for testing decode, timing and transport.
It does not decode MP4, WebM or YouTube video.

## Try the demo

From `~/myos` in WSL, use a fresh output name for the data disk. The disk
maker refuses to overwrite an existing image or save disk.

```bash
python3 tools/run_logged.py -- bash build.sh
python3 tools/run_logged.py -- python3 tools/make_video_disk.py build/phase31-data.img
qemu-system-x86_64 -m 64M \
  -drive format=raw,file=build/myos-current.img,if=floppy -boot order=a \
  -drive format=raw,file=build/phase31-data.img,if=ide,index=0 \
  -audiodev wav,id=snd,path=build/phase31-playback.wav \
  -device sb16,audiodev=snd
```

At `myos>`, type `video play /home/demo.myv`. The player shows a moving
colored block for three seconds. Press Space to pause/resume, Left/Right to seek one second backward/
forward, and Esc or q to stop early. It returns to the Shell at the end. Close QEMU before opening the
captured `build/phase31-playback.wav`; the WAV backend finalizes it on exit.
A live host audio backend may be substituted for QEMU's WAV backend where
configured.

The clip generator also writes `build/phase31-demo.myv`. You may package an
existing MYV1 file without altering it:

```bash
python3 tools/make_video_disk.py build/another-new-disk.img \
  --input path/to/clip.myv --name clip.myv
```

Then use `video play /home/clip.myv`. The file must be at most 65536 bytes.

## MYV1 file format

All integers are unsigned little-endian. The 24-byte header is:

| Offset | Bytes | Meaning |
|---|---:|---|
| 0 | 4 | ASCII `MYV1` |
| 4 | 2 | Width, 1–160 |
| 6 | 2 | Height, 1–120 |
| 8 | 2 | Frames per second: 5, 10, 20 or 25 |
| 10 | 2 | Frame count, 1–60 |
| 12 | 4 | PCM rate, exactly 11025 Hz |
| 16 | 4 | PCM sample count, exactly frames × 11025 / fps |
| 20 | 2 | Palette colors, 1–16 |
| 22 | 2 | Flags, zero |

The header is followed by RGB888 palette entries (three bytes each), a
uint16 compressed-length table (one entry per frame), the frame streams in
sequence, and the unsigned 8-bit mono PCM stream. Each frame stream is a
sequence of (run length, palette index) byte pairs, in row-major order. A
run length of zero, an out-of-range index, an incomplete or overlong frame,
a truncated table, or extra trailing bytes is rejected before playback.
Frames are independently decodable, allowing late frames to be skipped.

The supplied sample is 80×60, 10 fps, 30 frames, four colors, 3 seconds
and 36051 bytes. All pixels and PCM are generated by this repository; no
third-party media or codec license is required for the demo.

## Timing and requirements

PIT ticks at 100 Hz are the shared clock. The player queues the clip's PCM
once, starts the clock, renders the matching frame, skips a late frame rather
than slowing audio, and stops SB16 when playback ends. Pause stops SB16 and
holds the elapsed tick count; resume queues the remaining PCM from that
position. Left/Right seeks one second, clamps to the final frame, redraws
immediately, and requeues PCM from the new position when playing. Seeking
while paused keeps both picture and sound paused. Starting a clip discards
any earlier tone/WAV queue, since this prototype has only one audio client.

The player scales frames by an integer factor up to 4 on an off-screen
surface and presents to an 800×600×32 framebuffer. It needs that
framebuffer (or at least 640×480) and an emulated SB16. No framebuffer
or SB16 gives an explicit error. The sample's v2 data disk and playback
worked at 32 MiB RAM; 64 MiB is recommended. At 16 MiB the large v2 data
disk does not mount, and the Shell rejects playback without crashing.
Clip and software audio queue limits are 64 KiB. This is not a general
streaming pipeline; seek is limited to the loaded MYV1 clip.

## Verified tests

```bash
python3 tools/run_logged.py -- python3 tests/test_video.py
python3 tools/run_logged.py -- python3 tests/test_system.py
python3 tools/run_logged.py -- python3 tools/release.py build
python3 tools/run_logged.py -- python3 tests/test_video_packages.py
python3 tools/run_logged.py -- bash build.sh
```

QEMU acceptance checks moving framebuffer pixels, 25+ decoded frames
rendered within one 10 fps frame interval (10 PIT ticks) of their targets, audible
SB16 WAV output with ~440 Hz and ~660 Hz portions, pause/resume/stop,
malformed RLE rejection, 16 MiB graceful failure, 32 MiB playback, and
packaged BIOS and UEFI images. Testing uses synthetic original media.
This is a QEMU baseline only; physical sound/video hardware and actual
online YouTube playback remain separate milestones.
